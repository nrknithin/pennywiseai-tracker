# Fork changes — every upstream file Fin touches

Fin is a private fork of [`sarim2000/pennywiseai-tracker`](https://github.com/sarim2000/pennywiseai-tracker),
branched from `c512c7c` (15 Sep 2026, schema v62). Spec `05-build-release.md` §5.6 requires
that fork changes live in **new files** wherever possible, and that every edit to an existing
upstream file is listed here with a reason. This file is the audit of that rule.

Keeping this list short is the point: the smaller the diff against upstream, the cheaper the
quarterly rebase.

## Upstream files edited

| File | Why |
|---|---|
| `app/src/main/java/com/pennywiseai/tracker/data/database/PennyWiseDatabase.kt` | Unavoidable. Room requires every entity and DAO to be declared on the `@Database` class. Bumps `SCHEMA_VERSION` 62 → 63, registers the five M1 entities and their DAOs, and adds `AutoMigration(62, 63)`. No existing entity, DAO or migration was altered. |
| `app/src/test/java/…/usecase/DeleteTransactionUseCaseTest.kt`<br>`app/src/test/java/…/usecase/RestoreTransactionUseCaseTest.kt`<br>`app/src/test/java/…/receiver/NotificationActionReceiverTest.kt` | Consequential, not a choice. Each declares a hand-written `TestDb : PennyWiseDatabase()` that stubs every DAO with `error("unused")`, so adding five DAOs to the database class makes them abstract-incomplete and the test source set stops compiling. Five stubs added to each, in the file's existing style. No test logic touched. |
| `app/src/main/java/com/pennywiseai/tracker/PennyWiseApplication.kt` | Two additions, `+20/-0`: an injected `EmailAccountConfigStore` and a coroutine that calls `EmailSyncWorker.enqueuePeriodic` on process start, beside the `RecurringTransactionWorker` schedule upstream already arms there. Nothing else in the class was touched. The schedule cannot live in a new file: `Application.onCreate` is the one place WorkManager can be re-armed after a reboot or an app update, and it needs the stored sync interval, which is why it is a `launch` while the line above it is not. |
| `.gitattributes` (new file) | Pins LF in both index and working tree. The clone was made with `core.autocrlf=true`, which left 374 files as CRLF in the working tree while the index held LF *and cached the CRLF size*, so git reported them clean while their bytes differed. That silently broke `SupportedBanksDocTest` and `BankSamplesDocTest`, which compare generated LF text to the checked-in file. |
| `.gitignore` | `+4/-0`: a four-line stanza at the end (`.gitignore:110`) that ignores `spec/`. The 50-file specification is derived from the owner's real mailbox, so it stays on disk and out of the history (upstream `CLAUDE.md` hard constraint 4, spec 04 §4.5). | `app/build.gradle.kts`, `gradle/libs.versions.toml`, `app/proguard-rules.pro`, `app/src/main/res/xml/backup_rules.xml`, `app/src/main/res/xml/data_extraction_rules.xml` | Additive only: the JavaMail, jsoup and security-crypto dependencies, their R8 keep rules and packaging `pickFirsts`, and backup exclusions for the credential store. ## Deviations from the spec, and why

These are places where following the spec literally would have produced code that does not
compile, does not run, or loses data. Each is also commented at the site.

| Spec says | Fin does | Why |
|---|---|---|
| `02-architecture.md` §2.2 puts new parser code in `parser-core/src/commonMain` | It goes in `src/main/kotlin` (wired as `jvmMain`) | `commonMain` holds one file upstream and cannot see `java.math.BigDecimal`, which `ParsedTransaction` and every amount depend on. All 168 existing bank parsers live in `src/main/kotlin` for the same reason |
| `03-data-model.md` §3.5 lists a `DueKind` without `UTILITY_BILL` or `LOAN_PRECLOSURE`; `12-email-parsers.md` emits both, plus `SUBSCRIPTION_CHARGE` | `SUBSCRIPTION_CHARGE` → `SUBSCRIPTION`; `UTILITY_BILL` and `LOAN_PRECLOSURE` added to the enum | The three names in file 12 have no home in file 03's list, so those parsers could not be persisted at all. Adding an enum value needs no migration (§3.5) |
| `03-data-model.md` §3.3 files `sync_runs`, `transaction_sources` and `due_sources` under M2 (v64) | They are created at v63 | M1's own pipeline writes all three from its first run (spec 11 §11.3 step 2, §11.4 steps b and f). `ignore_rules`, `sender_overrides` and `never_merge_pairs` genuinely do wait for M2 |
| `12-email-parsers.md` §12.10 seeds `order-update@amazon.in` and `shipment-tracking@amazon.in` as dropped marketing | They are not dropped | `24-receipts-shopping.md` §24.2 names `order-update@` as a receipt source and R-24-01 needs its status progression. Ignore rules run first and short-circuit, so seeding them would make M5 unimplementable |
| `12-email-parsers.md` §12.10 drops any subject containing `offer`, `deal`, `sale`, `IPO`, `survey` or `%` | Those match on word boundaries; `%` only after a digit | As plain substrings, `sale` drops "wholesale" and `%` drops any subject quoting a rate — including real bank mail. Dropping a genuine bill is silent data loss |
| `12-email-parsers.md` §12.11 lists `MM/dd/yyyy` last in one ordered list of date patterns | When a sender is flagged `preferDMY = false`, US ordering is tried **first** | Listed last, `03/09/2026` parses as 3 September before the US pattern is reached — so every Xsolla date with a day ≤ 12 would be silently wrong |
| `06-test-plan.md` §6.1 puts `PiiLintTest` in `app/src/test/` | It lives in `parser-core/src/test/` | There it runs in the two-minute `./init.sh parser` loop rather than only in the Android unit-test job. It still scans `app/` |
| `06-test-plan.md` §6.2 redacts every card suffix to the one literal `1234` | Fixtures and tests use a spread of invented suffixes — `1234`, `4321`, `5432`, `5678`, `4821`, `4408`, `8812`, `8765` — assigned per fixture, none of them the owner's | Multi-account behaviour cannot be tested when every record names the same instrument. Spec 14 §14.3's L5 guard ("the two sides must name *different* instruments"), §14.5's own-account list, and the card-vs-account split all turn on two records disagreeing about the last-4; with one literal everywhere those cases are unwritable, and a genuine cross-account merge bug would pass every test. §6.2's actual requirement — that no digits are copied out of the mailbox — is kept in full: each value is chosen, not observed. `PiiLintTest` cannot police this either way, since a four-digit suffix has no distinguishing shape (the test says so in its own KDoc); it is kept by writing fixtures redacted, which is what §6.2 is for |
| `14-dedup-and-linking.md` §14.3 guards that "email never twins another email" | The guard compares channel **and** parser template id | HDFC sends H7 and H8 for the same card charge and spec 10 §10.8 requires them to collapse. As written the guard and that requirement cannot both hold |
| `14-dedup-and-linking.md` §14.3 L4 says a gateway receipt "never creates a transaction" | A non-bank message creates a transaction only when all three hold: `parser-core` has a transaction parser that claimed it, dedup found no existing transaction at L0–L5 inside the gateway window, and the parsed record names the instrument that was debited (`accountLast4 != null \|\| isFromCard \|\| fromAccount != null`). Otherwise it is link-only, logged `GATEWAY_LINK_ONLY` | `12-email-parsers.md` maps Razorpay RZ1, Cashfree CS1, CRED C2 and PGSharp P2 to transactions, which L4 as written forbids. Reading L4 as "never creates a *second* transaction for money a bank already reported" satisfies both: a receipt for a charge the bank also announced links, and a charge on an instrument no tracked bank reports (PGSharp's USD card) is still recorded instead of lost. A gateway-origin transaction is flagged so the bank's later alert takes over as primary source |
| `14-dedup-and-linking.md` §14.2 puts `cleanMerchant()` inside the dedup rules, while `02-architecture.md` §2.1 forbids parsing regex in `:app` | `cleanMerchant` and the body-hash normaliser live in `:parser-core` (`text/Cleaners.kt`, `text/BodyNormaliser.kt`); `DedupEngine` and `EmailBodyExtractor` call them | Both are regex text handling. It also keeps `body_hash` stable: the hash is persisted, so its normaliser must never be quietly re-implemented on the app side |
| `11-email-channel.md` §11.5 step 4 says `body_hash = md5` of the normalised body, unconditionally | A body whose normal form is empty (an image-only mail, or one that is nothing but links) stores `body_hash = ""` | md5 of the empty string is one fixed value that *every* bodyless mail would share, and dedup layer L0 (14 §14.3) merges on equal body hashes — two unrelated image-only mails would collapse into one transaction. Unknown is recorded as unknown (01, C7); `""` means "no evidence", never a match |
| `11-email-channel.md` §11.5 steps 1–2: prefer `text/plain` ≥ 40 chars, "else `text/html`" | When the HTML converts to nothing, a short `text/plain` part is used rather than discarded | The spec is silent about a mail whose only body is a one-line text part. Dropping it would store no body at all and lose the only evidence the Email Log could show |
| `11-email-channel.md` §11.5 step 2 says "collapse whitespace runs" | Whitespace is collapsed *within* a line, each line is trimmed, blank lines are dropped, and a newline inside an HTML text node counts as whitespace rather than a line break | Wrapping is chosen by the transport, so keeping it would make `body_hash` differ between two deliveries of one mail. The text-node rule is what HTML means, and it is what keeps a label and its value on one line: every pretty-printed mail puts a newline between `</td>` and `<td>`, and honouring it would break the cell join that 12 §12.4/§12.5/§12.7 parse against |
| `14-dedup-and-linking.md` §14.3 L2/L3 require "same type" | They require the same *direction*: money out (EXPENSE, CREDIT, TRANSFER, INVESTMENT) or money in (INCOME) | One charge is typed differently by each channel — the SMS parser says EXPENSE, the card email says CREDIT, a card bill paid from savings says TRANSFER. Requiring an identical `TransactionType` would split every twin pair §14.1 lists, which is the outcome dedup exists to prevent. Direction is the part of the type that cannot differ for one event, and it is what keeps a refund out of L1 and inside L5 |
| `14-dedup-and-linking.md` §14.3 matches on "the 12-digit reference", and guards on "different references" | References are compared digits-only with a 6-digit floor, and one reference that contains the other counts as agreement, not conflict | Bank references are not always 12 digits (IMPS and card refs run 9–16) and several templates print only the tail of an RRN. Comparing a 3- or 4-digit fragment, or calling a tail a conflict, blocks a real merge and leaves the user with a duplicate transaction |
| `14-dedup-and-linking.md` §14.3 L4 matches "order id **or** amount+merchant" | Both branches also require the amount to agree within `gatewayToleranceAbs` | An order id that matches a charge of a *different* amount is a partial capture or a second charge on the same order. Linking those hides real money, which is the opposite of what a receipt is for |
| `14-dedup-and-linking.md` §14.3 L5 gives the reference branch no window ("10 min / ref") | The reference branch is bounded by `upiRefWindowHours` (24 h), and the two sides must name different instruments | Bank references are recycled eventually and the two legs of a transfer never arrive a day apart. The instrument test is what stops a refund — same account, same reference, opposite direction — from being absorbed into the original charge and silently deleted |
| `14-dedup-and-linking.md` §14.3 L0 matches an "identical `transaction_hash` (same normalised body)" with window ∞ | The body-hash branch additionally requires the same **source identity**: the same channel, and either the same RFC 5322 Message-ID or the same sender *and* message timestamp (`MessageIdentity`). The `transaction_hash` branch keeps the unguarded ∞ window | L0 skips every other guard, so on body text alone it merges any two messages that read alike. `BodyNormaliser` keeps digits, but a template with no date, no reference and a fixed amount ("Rs 649.00 debited for your subscription") hashes identically for two genuinely separate charges, and L0 would collapse them and delete a month of money. §14.3 scopes L0 to "exact re-delivery (Gmail duplicate, SMS restore)", and identity is precisely what a re-delivery keeps and a second charge cannot reproduce. The hash branch needs no such guard: `transactions.transaction_hash` is a unique index, so a hash equal to a stored one can only belong to that row |
| `14-dedup-and-linking.md` §14.5 types the credit leg of an own-account transfer TRANSFER rather than INCOME | `DedupInput.direction` / `DedupCandidate.direction` carry which leg a record is, and every layer reads the leg from there before falling back to the type | Once both legs are typed TRANSFER the type can no longer tell them apart. Reading the leg off the type makes both legs "money out", so L1 merges them on their shared reference — recording `UPI_REF` and absorbing one leg into the other — while L5, which needs opposite legs, never fires. Null still means "read it off the type", which is how this app stores a transfer: on the account the money left |
| Nothing in the spec says what an empty `currency` compares as | An unknown currency never equals a known one; only blank-vs-blank matches | Treating blank as a wildcard does not merely merge — it *assigns* the existing transaction's currency to a record that never named one, inventing the value that decides whether 5.00 is five rupees or five dollars (01, C7; upstream `CLAUDE.md` constraints 1–2) |
| `11-email-channel.md` §11.2 states every setting as a range to clamp to | `initialLookbackDays` snaps **upward** to the next of 30/90/180/365, and anything past 365 becomes 0 = all mail; `port` falls back to 993 rather than clamping | Clamping the lookback downward is data loss that cannot be undone — mail outside the first window is never looked at again, because the UID watermark moves past it (R-11-04). An out-of-range port, by contrast, is a typo rather than a preference, so 0 becoming port 1 would only produce a confusing connection error |
| The design gives `AppPassword` one way out, `revealForImapLogin()`, and has `PiiLintTest` assert it has exactly one call site | There are two accessors: `revealForImapLogin()` for `JavaMailImapClient` and `revealForStorage()` for `EncryptedEmailCredentialStore` | The credential store is handed an `AppPassword` and has to write its characters into `EncryptedSharedPreferences`, so an exit for persistence has to exist somewhere. Two narrowly-named accessors keep the IMAP rule checkable — one shared accessor would make "exactly one call site" impossible to state. That lint now exists: `PiiLintTest` blanks comments, ignores the one occurrence preceded by `fun` — the declaration in `EmailCredentialStore.kt` — and fails the build on any second caller. `revealForStorage()` is deliberately outside the rule, for the reason above |
| `47-email-settings.md` E60 and `28-settings-customization.md` §28.3 list `settings.email.disabledSenders` | `EmailAccountConfig` has no such field in M1 | The per-sender enable list is a screen-47 editor that arrives with the rest of the settings backbone in M2, and the design contract for `EmailAccountConfig` omits it. `ignoredSenders` covers what M1 actually needs (the extra senders handed to `IgnoreRules.evaluate`). Adding the field later costs nothing: every field has a default |
| `11-email-channel.md` §11.3 step 8 fetches message bodies "lazily per message" | `MailboxSession.fetch` returns `FetchedMessage` with the body already extracted, inside the still-open session | A JavaMail `Message` is a live handle into an open folder and throws once that folder closes, so a lazy body would fail at a distance — inside the worker's Room transaction, after the run had moved on. Extracting per batch inside the session costs one pass and keeps every `javax.mail` type behind `JavaMailImapClient` |
| `20-dues-commitments.md` §20.5 step 3 bounds the settlement window as `[txn.date − before, txn.date + after]` with `before/after = earlyPayDays (45) / latePayDays (60)` | `PlausibleDueSettler` uses `[txn.date − latePayDays, txn.date + earlyPayDays]` | The spec's own pairing reads backwards, and §20.8's worked case settles it: an Axis statement due 1 October paid on 16 September is "early payment inside `earlyPayDays`". Early is therefore how far *ahead* a bill may be dated, late how far *behind*. Taken literally, paying 50 days late would fall outside a 45-day window while `latePayDays` 60 sat unused |
| `11-email-channel.md` §11.4 lists the skip reasons `IGNORE:` · `NO_PARSER` · `UNKNOWN_SENDER` · `NON_TXN` · `DUPLICATE:` · `ERROR:` · `RECEIPT_ONLY` | A seventh, `NOT_SAVED:<reason>`, is written when step g's save path refuses the transaction | `SmsTransactionProcessor` can refuse a save for three legitimate reasons the spec does not consider — a blocking rule, a duplicate hash, a row the user deleted. The alternatives were to log a working rule as `ERROR:` (which makes correct behaviour look like a defect) or to write nothing at all (which loses the message from the Email Log). The refusal text is slugged and capped at 40 characters so a throwable's message cannot reach the column intact |
| `11-email-channel.md` §11.4 e also does `unrecognized.add(channel=EMAIL, row.id)` for a known sender | M1 writes nothing; the call is a `UnrecognisedRecorder` seam whose default is a no-op | `unrecognized_sms` has no `channel` column at v63, so an email filed there would make screen 49 claim an email is an SMS. Nothing is lost: step e has already written `NO_PARSER`, and `EmailMessageDao.observeBySkipReason` is what the Email Log filters on. The seam means M2 fills this in without touching the pipeline |
| `11-email-channel.md` §11.4 h ends with `balances.record(saved)` and `planRecomputer.markDirty()` | Balances are left to the saver, and the plan flag is reported rather than set | `SmsTransactionProcessor.saveParsedTransaction` already records the balance for every transaction it writes, so calling it again here would double-count. `markDirty` is a per-*run* action in §11.3 step 22; doing it per message would be five hundred writes to say one thing, so `IngestResult.changedMoney` carries the answer up to the worker |
| `01-product-overview.md` constraint C7 (never invent a value) vs `11-email-channel.md` §11.3 step 15, which logs a received time for every message | `INTERNALDATE`, else the `Date` header, else the current instant — the last branch is commented at the site in `JavaMailImapClient.headerOf` | `email_messages.received_at` is not nullable and R-11-05 says the message is logged whatever else fails. RFC 3501 makes `INTERNALDATE` mandatory, so the fallback is unreachable against a compliant server; dropping a bank mail because a header was malformed would be the larger loss |
| `03-data-model.md` §3.2 files `has_attachments` and `attachment_names` under **M2**, in the 63→64 migration | Both are columns of `email_messages` at **v63** | `EmailBodyExtractor` already produces both at M1 (§11.5 step 3) and R-11-12 requires the names be recorded. Neither can be recovered later: only the extracted text is kept, and it is trimmed after `retainBodiesDays`, so a mail's attachments would be unknowable by the time M5's PDF rules want them. **No new migration is needed and none was written**: `email_messages` does not exist at v62, so `AutoMigration(62, 63)` creates the table from the entity, both columns included. `app/schemas/com.pennywiseai.tracker.data.database.PennyWiseDatabase/63.json` **is** exported and tracked, and it lists them, so the exported schema and the entity agree — which is what Room validates at build time. (This row used to justify itself with "v63 is unreleased with no `63.json` exported yet". That was true when it was written and is not now. The conclusion is unchanged, because the auto-migration creates the columns either way; what the export adds is that any further change to `email_messages` must re-export `63.json` in the same commit, until v63 ships and the next change needs a 63→64 migration instead.) The third M2 column, `receipt_id`, genuinely waits — nothing writes it before M5 |
| `11-email-channel.md` §11.2 states the email settings simply persist | A `fin_email_settings` file that cannot be parsed is replaced with an empty one (`ReplaceFileCorruptionHandler`), and a read that fails with any `IOException` yields the documented defaults instead of throwing | DataStore surfaces a damaged file as `CorruptionException` from **every** read *and* every write, permanently — `edit()` reads before it writes, so without the handler the settings could not even be re-entered from screen 47. The cost is losing the address, folder and watermark, all re-enterable, and R-11-08 recognises the mail a reset watermark re-fetches. ## Still open — decisions for the owner

Recorded here so they are not lost; none blocks M1.

- **`05-build-release.md` §5.5 vs upstream `CLAUDE.md`.** The spec wants `versionName = "fin-0.2.0+pwc512c7c"`; upstream makes it a hard constraint that `scripts/release.sh` owns the version and it is never hand-edited. The fork must either break that rule or replace the script.
- **The `personal` flavor cannot compile as specified.** `05-build-release.md` §5.2 defines it as "`fdroid` behaviour plus cloud", but Gradle flavors in one dimension do not share source sets, and the four classes it needs live in `app/src/fdroid/`. Needs a shared source set (e.g. `app/src/unlocked/`) added to both flavors.
- **Backup and cloud snapshot specify two incompatible encryption schemes for the same bytes.** `27-backup-drive.md` R-27-03 derives the key straight from the passphrase; `08-cloud-services.md` §8.5.3 calls it the same payload but wraps a random DEK. The `PWFINENC1` container has no slot for a wrapped key, so one of the two has to change before backups exist.
- **`androidx.security:security-crypto` has no stable release.** The design names `1.1.0`; Jetpack Security Crypto was deprecated by Google and 1.1.0 never shipped, so `libs.versions.toml` pins `1.1.0-alpha06` — the version the design itself lists as the fallback, and one that is certain to resolve. If a stable release exists by the time this builds, it is a one-line bump. The longer-term replacement is a hand-rolled Android-Keystore AES-GCM wrapper, which is the same primitive `08-cloud-services.md` §8.5.3 already needs for `fin_dek_wrap`.
- **`11-email-channel.md` R-11-01 fixes the app password at 16 characters; `47-email-settings.md` E27 offers "Other IMAP provider".** `AppPassword.parse` enforces 16, as the design contract specifies, so a non-Gmail account cannot be configured today. Either the length check becomes Gmail-host-only, or the "other provider" expander is dropped.
